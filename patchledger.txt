GOAL
Add a living force-directed / gravity graph to Memory Space as a new first-class visual surface.

The graph is NOT a replacement memory database. Existing Memory Space remains the source of truth. The graph reads the existing workspace and visualises it.

Core idea:
- every Space / memory / note / job / repo can become a node
- related things are connected by lines
- important or heavily linked nodes pull closer toward the centre
- similar memories naturally cluster
- weak / old material drifts further out
- active jobs or hot memories can glow / pulse
- clicking a node opens the real existing memory / inspector behind it
- Wizz / DevMaster can ultimately act as the central/root node across the wider system

HARD BOUNDARIES FOR THIS JOB
- DO NOT redesign Memory Bridge
- DO NOT change OAuth / MCP / provider connection behaviour
- DO NOT change external AI proposal rules
- DO NOT change trusted-memory approval boundaries
- DO NOT replace the current memory engine or lifecycle
- DO NOT rewrite the app architecture
- graph code should be isolated from the existing memory core
- moving graph nodes must never alter/corrupt memory records
- normal Memory view stays available, but can become visually smaller so the graph becomes the front-line feature

VISUAL / GRAVITY RULES
- active Space = strong central gravity point for that Space view
- critical / important memories = larger nodes
- highly connected memories = stronger pull / more central
- recently touched memories = brighter
- old / weakly connected memories = further outward
- locked memories = distinct solid ring
- pending AI proposals = later pulse/glow state
- archived / superseded memories = later faded/history-only state
- explicit relationships = strongest edge
- revision relationships = real edge
- same project/tag/entity = medium edge later
- calculated similarity = weaker inferred edge later
- agent/job activity = animated ring/pulse later

IMPLEMENTATION SHAPE
Prefer an isolated Canvas-based force graph so the app can eventually handle hundreds or thousands of nodes without turning the DOM into a brick.

Keep graph UI/state separate from durable memory data. Persist only harmless view state such as node positions, zoom and pan in a separate graph storage key if needed.
